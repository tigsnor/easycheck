# PlateNote 로컬 데이터 안전 기준

PlateNote 단일 사용자 버전은 실험과 Plate 데이터를 앱 문서 디렉터리의 JSON 파일로 저장합니다. 저장 중 앱 종료나 파일 손상이 발생해도 마지막 정상 데이터를 최대한 보존하기 위해 다음 규칙을 사용합니다.

## 파일 구성

각 원본 JSON 파일에는 보조 파일이 생길 수 있습니다.

- `<name>.json`: 현재 데이터
- `<name>.json.bak`: 직전 정상 데이터
- `<name>.json.tmp`: 저장 중 사용하는 임시 파일
- `<name>.json.bak.tmp`: 직전 정상본을 교체하기 위한 임시 파일
- `<name>.json.recovery.tmp`: 복구 내용을 원본으로 교체하기 위한 임시 파일
- `<name>.json.corrupt-<시각>`: 복구 또는 교체 전에 별도 보존한 손상 원본

임시 파일과 backup은 앱 내부 복구용이며 사용자가 직접 수정하지 않습니다.

## 안전 저장 순서

1. 새 데이터를 `.tmp`에 쓰고 디스크 반영을 요청합니다.
2. 임시 파일을 다시 읽어 JSON과 데이터 구조를 검증합니다.
3. 현재 원본이 정상인 경우 `.bak.tmp`에 복사하고 flush한 뒤 `.bak`을 교체합니다. 이 과정에서 원본은 이동하거나 삭제하지 않습니다.
4. 원본이 손상된 경우에는 별도 `.corrupt-<시각>` 파일로 보존합니다.
5. 검증된 임시 파일을 원본 경로로 rename하여 교체합니다. 교체가 실패해도 기존 원본은 그대로 남습니다.

손상된 원본은 정상 backup을 덮어쓰지 않습니다.

동일 앱 isolate 안의 같은 파일 읽기·쓰기·삭제는 저장소 인스턴스가 달라도 순서대로 처리합니다. 실험 목록과 템플릿 목록의 read-modify-write도 하나의 작업으로 묶어 동시 저장으로 항목이 누락되지 않게 합니다. 여러 프로세스 간 잠금이나 여러 파일을 아우르는 transaction을 보장하는 것은 아닙니다.

삭제는 backup과 임시 파일을 먼저 제거하고 원본을 마지막에 지웁니다. 삭제 중 종료되어도 이미 삭제된 원본이 backup에서 자동으로 되살아나지 않도록 하는 순서입니다.

## 자동 복구

원본 파일을 읽을 때 다음 오류가 발생하면 backup을 확인합니다.

- 빈 파일
- 잘린 JSON 또는 잘못된 JSON 문법
- 예상한 List/Object 구조가 아닌 파일
- 지원하지 않는 schema version
- 필수 모델 필드가 없는 데이터

Backup이 정상이라면 이를 원본으로 복원한 뒤 데이터를 불러옵니다. 자동 복구가 끝나면 앱 전체에서 복구 안내 창을 표시하고 즉시 전체 백업을 만드는 것을 권장합니다. 원본과 backup이 모두 손상되면 오류를 숨기지 않고 repository 호출자에게 전달합니다.

원본이 없는 경우에도 backup을 먼저 검사합니다. 사용 가능한 backup이 없으면 검증을 통과한 `.tmp`로 최초 저장 중단 상태를 복구할 수 있습니다. 원본·backup·임시 파일이 모두 없을 때만 새로운 빈 저장소로 처리하며, 복구 후보가 남아 있으나 모두 손상되었으면 오류를 표시합니다. 손상 원본은 복구 전에 별도 보존합니다.

Plate, 템플릿, Plate 이력 snapshot은 행·열 크기에 맞는 전체 well, 중복되지 않는 좌표, 유효한 그룹 참조, 유한한 수치를 요구합니다. 필수 well 배열이 없는 데이터는 정상 legacy 데이터로 간주하지 않습니다. 기존의 well 배열을 가진 legacy 파일과 선택적인 이력 필드는 계속 지원합니다.

## 편집과 결과 입력 보호

- 실험 저장 중 새로 입력한 내용은 저장 요청 당시의 값과 별도로 비교하여 미저장 상태를 유지합니다.
- Plate 저장 실패 시 같은 변경을 재시도하거나 명시적으로 폐기하기 전까지 추가 변경과 화면 이탈을 보호합니다.
- 개별 well의 잘못된 숫자와 비유한 수치는 저장을 차단합니다. 빈 값으로 지우는 동작과 숫자 오타를 구분하고 편집 시 원래 수치의 정밀도를 유지합니다.
- 결과 행렬의 내부 빈 행은 좌표를 유지하며, 중복 행 좌표와 좌표 표기 혼용은 적용을 차단합니다. 숫자만 있는 첫 행이 열 제목과 구분되지 않으면 사용자가 첫 행 해석을 선택해야 합니다.

## 새 실험과 설계 복제

템플릿을 선택하지 않은 새 Plate는 빈 96-well로 시작합니다. 예시 농도와 그룹은 자동 생성하지 않으며 기존 저장 Plate는 수정하지 않습니다.

`설계 복제`는 기본정보(프로젝트·유형·연구자·세포수·태그), 단계 제목, 자원 정보와 Plate 배치(그룹·역할·농도·부피·반복)를 새 ID의 초안으로 복사합니다. 단계 완료·타이머, 실험 완료 시각, 결과·결과 단위·분석 제외, 실험/Plate/well 메모와 모든 변경·가져오기 이력은 초기화합니다. 자원 정보의 설명은 유지됩니다. 원본에 Plate가 없으면 복사본도 Plate 없이 시작하며 첫 편집 시 빈 Plate를 만듭니다.

복제는 원본을 다시 읽고 새 ID가 사용 가능한지 확인한 뒤 Plate를 먼저 저장하고 실험을 마지막에 등록합니다. 저장 오류 시 새 ID에 해당하는 데이터만 정리하고, 정리 오류도 사용자에게 전달합니다. 앱 강제 종료까지 포괄하는 다중 파일 트랜잭션은 아니며, Plate 저장과 실험 등록 사이에 종료되면 목록에 연결되지 않은 복사본 Plate가 남을 수 있습니다. 원본 파일은 이 과정에서 쓰거나 삭제하지 않습니다.

## Schema version

Experiment와 Plate 파일은 다음 envelope로 저장합니다.

```json
{
  "schemaVersion": 1,
  "data": {}
}
```

기존 버전에서 사용하던 최상위 Experiment List와 Plate Object도 계속 읽을 수 있습니다. Legacy 파일을 읽은 뒤 데이터를 저장하면 version 1 envelope로 변환됩니다. 현재 앱보다 높은 미래 version은 임의로 읽지 않고 backup 복구 또는 오류 처리 대상으로 봅니다.

## 전체 백업 복원 안전성

전체 백업은 저장을 시작하기 전에 중복 ID와 실험-Plate 연결 관계를 다시 검증합니다. v2 백업은 실험·Plate·사용자 템플릿을 포함합니다. v1 백업은 계속 지원하며 템플릿은 변경하지 않습니다. 중복 템플릿 ID와 손상된 템플릿도 적용 전에 거부합니다. 복원 도중 실험, Plate 또는 템플릿 저장이 실패하면 이번 복원의 영향을 받는 기존 데이터를 snapshot으로 되돌리고, 새로 추가되던 데이터는 삭제합니다. Rollback 자체도 실패하면 원래 복원 오류와 rollback 오류를 함께 사용자에게 전달합니다.

## 손상된 데이터 전체 복구

현재 저장 파일을 읽지 못해도 백업 화면과 파일 선택은 열립니다. 이때 새 백업 내보내기는 비활성화되며, 사용자는 `손상된 데이터 전체 복구`를 선택할 수 있습니다. 병합과 달리 실험·Plate 목록은 선택한 백업 내용으로 대체됩니다. 적용 전 개수와 영향 범위를 확인받고, 처리 중 다른 편집과 이탈은 막습니다.

전체 복구는 기존 원본을 덮어쓰지 않습니다. 앱 문서 디렉터리의 `.platenote-restores/restore-<고유값>`에 새 데이터를 작성하고 실제 repository로 다시 읽어 검증합니다. 모든 준비가 끝나면 `platenote-storage.json`의 활성 폴더를 한 번의 rename으로 전환합니다. 전환 준비 파일 `.next`는 시작 시 자동으로 적용하지 않습니다. 따라서 준비나 전환 전에 실패한 폴더는 다음 실행에서도 활성화되지 않습니다. 기존 원본·이전 복구 폴더는 그대로 보존하며 자동 삭제하지 않습니다.

세 repository는 같은 활성 폴더를 매 작업마다 확인합니다. 같은 앱 isolate의 작업과 복구 전환을 직렬화하여 전환을 기다리던 저장은 새 폴더에 기록합니다. 유효하지 않은 활성 폴더 정보나 준비되지 않은 폴더는 빈 목록으로 처리하지 않습니다.

v1 백업으로 전체 복구하면 기존 템플릿 파일과 보조 파일을 그대로 새 폴더로 복사합니다. 따라서 기존 템플릿 자체가 손상되었다면 그 문제는 v1 백업으로 해결되지 않습니다. v2 백업은 템플릿도 포함된 내용으로 대체합니다. 복구 중 남은 폴더는 진단용으로 보존되므로 저장 공간 관리가 필요할 수 있습니다.

전체 복구의 새 폴더 전환과 달리, 기존 병합 복원의 rollback은 프로세스 내 예외 대응입니다. 병합 중 강제 종료의 다중 파일 원자성과 기기 전원 차단 시 파일시스템 내구성까지 보장하지는 않습니다.

## 남은 안전성 작업

- 사용자가 손상 원본과 backup 정보를 확인하는 상세 복구 화면
- 여러 단계의 복원 지점
- 첨부파일까지 포함하는 무결성 검사
- 실제 기기에서 저장 중 강제 종료 테스트
- 병합 복원의 앱 강제 종료 대응 및 보존된 복구 폴더의 조회·공간 관리
